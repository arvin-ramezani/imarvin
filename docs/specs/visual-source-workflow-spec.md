# Visual Source Workflow — VSRC

Status: documentation policy for #54 workstream A; images and owner approvals belong to a separate bounded issue/PR. Updated: 2026-10-12.
Authority: [decisions](../decisions.md), [Signal Studio](visual-system-spec.md), [public UX](public-ux-spec.md), [owner UX](owner-ux-spec.md), [media](media-evidence-spec.md), [accessibility](accessibility-responsive-spec.md), [engineering workflow](../engineering/spec-driven-development.md), and [UI skill policy](../engineering/ui-skill-policy.md).
Approval/index record: [visual-source registry](../visual-source-registry.md). #54 remains open until actual owner-approved, retrievable visual sources exist; this policy/PR alone cannot close it.

## 1. Scope and authority

- **VSRC01 — Applicability:** before meaningful new visual UI/layout work (screen, media-rich composition, substantive responsive redesign, notable multi-state component or material visual revision), require an approved source image for affected states. For small copy changes, nonvisual logic, accessibility-only fixes with no material appearance change, narrow bug fixes or minor local spacing, record `VISUAL SOURCE NOT REQUIRED` with reason and affected surface. A code change is not by itself a trigger.
- **VSRC02 — Authority:** canonical Markdown governs behavior, privacy, accessibility, copy truth, theme, content/asset identity and P16 motion boundaries; approved images govern appearance/composition **within** those contracts. Neither images nor Design QA introduce features, evidence, launch claims or approval of source project media. Conflict or insufficient facts → owner/Command Center; do not guess. The approved Signal Studio direction stays unchanged.
- **VSRC03 — Separation:** #54 workstream A creates this policy/registry in PR #55; [#56](https://github.com/arvin-ramezani/imarvin/issues/56) workstream B, in a **different image-design PR**, creates and obtains approval of actual image revisions. Later implementation/refactor/Design QA are separate bounded issues/PRs. No code/image/approval is authorized by the existence of this policy alone.

## 2. Visual source selection, coverage and provenance

- **VSRC04 — Real source:** permitted sources are an actual Figma frame, rendered mockup/image, reviewed screenshot or equivalent stable visual capture. A Markdown brief, text-only specification, generated prompt, or inaccessible image is **not** a visual source. Explicitly distinguish independently designed mockups from implementation-derived captures; the latter can only become a newly approved baseline, never evidence of prior design fidelity.
- **VSRC05 — Coverage:** each bounded image set begins with a screen/state matrix tied to exact canonical requirement/scenario IDs and specification revision(s). Cover **materially distinct** wide/narrow (include 320px when relevant), Light/Dark, representative rich/empty/no-media, loading/error/confirmation, and focus/interaction states. Reuse existing approved variants where appearance is unchanged; record rationale and exclusions rather than proliferating images. Static images do **not** establish keyboard, touch, zoom, motion, screen-reader or runtime behavior.
- **VSRC06 — Source registration:** record every proposed/approved/superseded source in the [registry](../visual-source-registry.md): stable ID + immutable revision/sha; actual durable retrievable file/frame/link; source type/provenance (including app-head for implementation capture); screen/route/component + state/content/capture permissions; dimensions/viewport/theme/focus; exact spec SHA + IDs; coverage/reuse/exclusions; owning issue/PR; approval actor/date/URL and status. Never overwrite approved bytes in place. Restrict evidence/project captures to confirmed permitted assets, not synthetic customer data.
- **VSRC07 — Owner approval:** owner must see the **actual** images and explicitly accept named IDs, revisions and variants with a durable comment/link before status becomes `APPROVED`. Generated/old screenshots and prior broad aesthetic approval remain `PROPOSED` until this gate. Rejected/replaced variants are `SUPERSEDED` with pointers and history. If the source changes, obtain approval for the changed revision and reevaluate dependent plans and QA.

## 3. Gate order and independent verification

- **VSRC08 — New visual slice:** canonical UX/specs + confirmed content → bounded visual-design issue → proposed actual images/registry variants → owner revision-specific approval → bounded implementation issue/plan → independent plan review where required → code/tests/reviews → independent Design QA. `image-to-code` or prototypes may help only under separate authorization; neither is a substitute for tokens, security/privacy, Next.js constraints, accessible behavior or runtime checks. Existing nonvisual exceptions follow VSRC01.
- **VSRC09 — Fidelity QA:** reviewer independently opens the **approved exact source** and running UI at matching route/state/content/viewport/theme, verifies typography, spacing/layout, palette, copy, imagery and responsive composition, and separately checks observable interactions. Report source ID/revision/approval link, exact implementation PR head SHA, environment and discrepancies. Missing/inaccessible/stale source → `BLOCKED — visual fidelity`; Markdown-only or screenshot-only inspection is not Design QA PASS. Keep other deterministic, independent/security and runtime gates separate.
- **VSRC10 — Recovery and reuse:** changing image revisions, UX scope, content truth or source availability invalidates affected downstream approval/plan/comparison evidence—not unrelated approved variants. Reuse by immutable reference when unchanged. No newly approved baseline can retroactively certify previous fidelity. Keep P16 owner UI motion-free and public motion separately reviewable; static images never prove motion or focus.

## 4. Worked handoff and migration example

**Representative workflow (illustrative, not an approval):** select the Home feature and Work detail based on PU01, VS01–VS06 and ME01–ME06; confirm O02 before any factual content-backed visual. Record distinct wide/narrow and Light/Dark variants, or explicit reused variants, in the registry as `PROPOSED`. Present each actual image/revision for owner signoff. Only after approval may a separately authorized implementation match it and an independent reviewer compare source/render at the exact implementation SHA. A text-only no-media state needs no fabricated screenshot; an unavailable/unconfirmed media asset is not evidence of intentional no-media design.

**PR #51:** its 40 implementation-derived screenshots are **candidate** new-baseline sources only, not preapproved designs. An owner may explicitly approve chosen exact captures with routes, states, variants and provenance; then conduct fresh independent source/render Design QA against the chosen approved baseline plus targeted loaded-image evidence. This cannot prove prior design fidelity or change #51's existing BLOCKED status, Security Review, Independent Review or runtime acceptance.

## 5. Completion and failure conditions

- **Policy check:** VSRC01–VSRC10 covered, registry prepared, canonical links and scenario IDs resolve, Markdown length limits pass; no application code or visual images in the policy PR.
- **Workstream B check:** actual retrievable images with approved exact revisions, coverage/reuse/exclusions and owner approval evidence are mandatory before #54 may close. If facts/permission are unknown, mark only affected mockups `BLOCKED — INPUT NEEDED`; other structurally grounded screens can proceed when permitted by the visual brief.
- **Fallback check:** missing source blocks only the affected visual gate, not an unrelated small nonvisual fix with documented VSRC01 exception. Missing project media does not justify invented captures or a false no-media claim.
