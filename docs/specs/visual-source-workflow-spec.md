## 1. Scope and authority

- **VSRC01 — Applicability:** before meaningful new visual UI/layout work (screen, media-rich composition, substantive responsive redesign, notable multi-state component or material visual revision), require an approved source image for affected states. For small copy changes, nonvisual logic, accessibility-only fixes with no material appearance change, narrow bug fixes or minor local spacing, record `VISUAL SOURCE NOT REQUIRED` with reason and affected surface. A code change is not by itself a trigger.
- **VSRC02 — Authority:** canonical Markdown governs behavior, privacy, accessibility, copy truth, theme, content/asset identity and P16 motion boundaries; approved images govern appearance/composition **within** those contracts. P18 authorizes **labelled synthetic fixtures** for mockups and non-production implementation/tests, not assertions about real project evidence, launches, media permission or working contact. Only actual publication needs O01–O03. Conflicts in behavior/scope → owner/Command Center; do not guess. P19–P26 scoped checkpoints govern combined Home, distinct Project/Story, owner arrangement, lifecycle and Contact. Older W43 Work evidence retains historical scope; unaffected Signal Studio/P17 guarantees remain. Open P19 decisions remain open.
- **VSRC03 — Separation:** #54 workstream A creates this policy/registry in PR #55; [#56](https://github.com/arvin-ramezani/imarvin/issues/56) workstream B, in a **different image-design PR**, creates and obtains approval of actual image revisions. Later implementation/refactor/Design QA are separate bounded issues/PRs. No code/image/approval is authorized by the existence of this policy alone.

## 2. Visual source selection, coverage and provenance

- **VSRC04 — Real source:** permitted sources are an actual Figma frame, rendered mockup/image, reviewed screenshot or equivalent stable visual capture. A Markdown brief, text-only specification, generated prompt, or inaccessible image is **not** a visual source. Explicitly distinguish independently designed mockups from implementation-derived captures; the latter can only become a newly approved baseline, never evidence of prior design fidelity.
- **VSRC05 — Coverage:** each bounded image set begins with a screen/state matrix tied to exact canonical requirement/scenario IDs and specification revision(s). Before generating affected images, verify the current companion UX/fixture/skill revisions against P19–P26 and record exact approved scoped IDs/revision; re-reconcile any new conflicts and defer still-open component/gallery/transaction variants. Use labelled P18 fixture data to cover materially distinct wide/narrow (320px where relevant), Light/Dark, rich/empty/no-media, loading/error/confirmation and focus states without waiting for actual project facts. Reuse unchanged approved variants with rationale and exclusions. Static images do **not** establish keyboard, touch, zoom, motion, screen-reader or runtime behavior.
- **VSRC06 — Source registration:** record each proposed/approved/superseded source in the [registry](../visual-source-registry.md): ID + immutable revision/sha, retrievable image/frame; source and fixture/real provenance (including app-head for real implementation capture); screen/route/state, fixture dataset, viewport/theme/focus; exact spec SHA + IDs, coverage/reuse/exclusions, issue/PR and owner approval actor/date/URL. Never overwrite approved bytes. Synthetic media slots are explicitly tagged **TEST ONLY** and never called authentic project Evidence. Asset-specific real-media proof is required only when actual media is used.
- **VSRC07 — Owner approval:** owner must see the **actual** images and explicitly accept named IDs, revisions and variants with a durable comment/link before status becomes `APPROVED`. Generated/old screenshots and prior broad aesthetic approval remain `PROPOSED` until this gate. Rejected/replaced variants are `SUPERSEDED` with pointers and history. If the source changes, obtain approval for the changed revision and reevaluate dependent plans and QA.

## 3. Gate order and independent verification

- **VSRC08 — New visual slice:** canonical UX/specs reconciled with P19–P26 + labelled P18 fixtures → bounded visual-design issue → proposed actual images/registry variants → owner revision-specific approval → bounded implementation issue/plan → independent plan review where required → code/tests/reviews → independent Design QA. `image-to-code` or prototypes may help only under separate authorization; neither is a substitute for tokens, security/privacy, Next.js constraints, accessible behavior or runtime checks. Existing nonvisual exceptions follow VSRC01.
- **VSRC09 — Fidelity QA:** reviewer independently opens the **approved exact source** and running UI at matching route/state/content/viewport/theme, verifies typography, spacing/layout, palette, copy, imagery and responsive composition, and separately checks observable interactions. Report source ID/revision/approval link, exact implementation PR head SHA, environment and discrepancies. Missing/inaccessible/stale source → `BLOCKED — visual fidelity`; Markdown-only or screenshot-only inspection is not Design QA PASS. Keep other deterministic, independent/security and runtime gates separate.
- **VSRC10 — Recovery and reuse:** changing image revisions, UX scope, content truth or source availability invalidates affected downstream approval/plan/comparison evidence—not unrelated approved variants. Reuse by immutable reference when unchanged. No newly approved baseline can retroactively certify previous fidelity. Keep P16 owner UI motion-free and public motion separately reviewable; static images never prove motion or focus.

## 4. Worked handoff and migration example

**Representative workflow (illustrative, not an approval):** select Home's combined identity/Featured Project hero, independent Story/More Projects previews and later About introduction (UXH01–UXH08), distinct Project and Story details (UXN01, UXC01–UXC06), and independent relationships/visibility (PS01–PS05). Confirm the latest public/media/navigation/owner companions and record their SHA before the image variant. Use explicitly fictional Project and Story fixtures (P18), including zero/one/many optional media and standalone/private-parent Stories; never invent Waiting Room claims or authentic captures. Home Experience has no required company page; details have no mandatory Problem/Decisions template. Apply the checkpoint's routine media usability defaults; use P26 UXH10/UXD03–UXD04/UXD08–UXD10 presentation (including vertical Project showcase); keep exact rendered sizing/player/inspection-return variants and UXD05 editor widgets deferred. Publishing minima (UXD06–UXD07) and P25 hierarchy remain approved. Include Home no-feature, published-label pin sorting, arrangement Apply, Project/Story minimum/no-media and Contact/Privacy states where meaningful. Register bounded wide/narrow and Light/Dark sources as `PROPOSED`, with exact spec revisions/IDs, then obtain exact-image owner signoff. Later authorized implementation uses matching fixtures for Design QA at its exact SHA. O01–O03 real facts remain required only before real publication.

**PR #51:** its 40 implementation-derived screenshots are **candidate** new-baseline sources only, not preapproved designs. An owner may explicitly approve chosen exact captures with routes, states, variants and provenance; then conduct fresh independent source/render Design QA against the chosen approved baseline plus targeted loaded-image evidence. This cannot prove prior design fidelity or change #51's existing BLOCKED status, Security Review, Independent Review or runtime acceptance.

## 5. Completion and failure conditions

- **Policy check:** VSRC01–VSRC10 covered, registry prepared, canonical links and scenario IDs resolve, Markdown length limits pass; no application code or visual images in the policy PR.
- **Workstream B check:** actual retrievable images with approved exact revisions, fixture provenance, coverage/reuse/exclusions and owner approval evidence are mandatory before #54 may close. Unknown real content or assumed project-owner permission never blocks fixture-only design; block only an attempt to include unverified **actual** customer/project media or make real-world publication claims.
- **Fallback check:** missing source blocks only the affected visual gate, not an unrelated small nonvisual fix with documented VSRC01 exception. Missing project media does not justify invented captures or a false no-media claim.
